# School ERP reference gap analysis

**Status:** In progress — evidence-led snapshot, 2026-10-23. This is not a claim that every route or workflow is complete.

## Scope and evidence

- Reference: [Multi School ERP demo](https://demo.multischoolerp.com/login) and its [role guide](https://docs.multischoolerp.com/guide/who-does-what), [permissions guide](https://docs.multischoolerp.com/school/roles-permissions), [student guide](https://docs.multischoolerp.com/school/students), and [fee setup guide](https://docs.multischoolerp.com/school/fee-setup).
- Direct reference observations in this pass: authenticated School Admin → `/school/dashboard`, `/school/students`, and `/school/collect-fees`, including the per-student collection view; Accountant, Teacher, and Parent selected workflows; Platform Owner and group/Branch Admin views. Parent read-only checks covered dashboard, fees/history, exams, homework, attendance and timetable. The reference Parent fee view exposed negative unpaid balances/discounts and multiple incomplete online payment attempts; those figures/statuses were not reconciled and are not correctness targets. Teacher could open a school-wide health roster containing blood-group data; treat as a potential scope concern pending policy verification, not a confirmed vulnerability. See `erp-browser-verification.md` for role-by-role evidence and remaining checks.
- Follow-up reference admission view `/school/students/create` exposed a five-part flow (academic, personal, parents, health/bank, documents), with class/section, opening due and parent/login details in the form. It was inspected read-only; no reference record was submitted. Local disposable-clone School Admin admission and subsequent tuition allocation/invoice/payment/report workflow are now browser- and DB-verified (see browser verification); the local registration UI and reference data fields still need a field-by-field parity decision, not wholesale copying.
- Local evidence: current `DEMOERP` database audit, route smoke test, experience verifier, focused Jest tests, plus dated manual checks in `.gsd/JOURNAL.md`. API smoke tests prove only the endpoints/assertions they exercise; they do not prove every UI action.
- Status meanings: **Working** = current targeted evidence exists; **Partial** = real functionality exists but a stated workflow/control remains incomplete; **Unverified** = evidence is insufficient or not yet gathered. Priority is implementation order, not severity.

## Explicit non-goals

Do not clone reference branding or copy its inconsistent dashboard KPIs. Do not add generic table controls or optional integrations before core workflows and tenant boundaries are verified. Keep current Nuxt/Express/Sequelize architecture and existing school configuration/data contracts.
